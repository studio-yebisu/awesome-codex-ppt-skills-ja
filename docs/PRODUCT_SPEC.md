# AIスライド制作スキル集：日本語で作って選べるコレクション

仕様策定：Astra / 2026-10-13。対象は今回のローカル初回実装。公開・正式採用の完了を示す文書ではない。

## 1. ユーザーの意図

出発点は `03a2cb0` の「209件・6カテゴリのAIスライド制作スキル集」。その豊かな選択肢を残し、実際に各スキルをこの環境で使って日本語の資料を制作し、完成作品を見てスキルを選び、自分でも使えるコレクションへ育てる。

翻訳した説明と上流へのリンクだけだった場所に、日本語で制作した実例、成果物、使うための依頼文、改善した派生スキル、実際に確かめた条件を加える。StudioYebisuが自分のプロジェクトとして、選定・制作・改善・保守を担う。原作者の成果を自作として名乗るという意味ではない。

ユーザーが見たいのは「このスキルで日本語の仕事の資料を作ると、こうなる」。スキルの説明スライドやサイト自身の紹介スライドでは、その判断材料にならない。「スライド事例を見る」を押すと、その場にプレイヤーが浮かび、実際の資料を最後まで見られる。気に入れば成果物を持ち帰り、同じスキルで自分の内容を制作できる。

### 前案から変える判断

| 前案の問題 | 今回の決定 |
|---|---|
| 209件を独立した少数の汎用自作スキルに置換 | 各掲載スキルの名前・作者・原典・分類を保ち、個別に制作例と改良を蓄積する |
| 209枚のカードと少数のデモを足すだけ | 制作例を入力からダウンロード、再制作までつながる恒久的な単位にする |
| 「日本語フォント」「スキルを選ぼう」を題材にする | 稟議・報告・研修・企画・登壇として内容が完結する資料を作る |
| 原典を参照したというだけで同じrendererを使う | 該当スキルの手順・テンプレート・変換器を使い、採用箇所と差分を記録する |
| 外観を完成度の根拠にする | 実ファイルの閲覧・編集可能性・再制作手順・日本語品質を確認する |

初期サイトへの回帰は目的と情報構造の回帰であり、使える技術部品まで破棄するGitの巻き戻しを要求しない。`docs/PROJECT.md`など旧案の方針と衝突する箇所は、この仕様と最新のユーザー発言に合わせて更新する。

## 2. 利用者に提供する体験

1. トップで「日本語の制作事例から探す」と「209件のスキルを探す」の両方が分かる。6カテゴリを常設し、元のコレクションを探す利用者も迷わない。
2. 用途（提案・報告・研修・企画・登壇等）や形式（編集可能なPPTX・Web）で制作事例を選ぶ。表紙だけでなく、図表や本文を含む中面も見せる。
3. 「スライド事例を見る」でフロート表示。前後送り、現在位置、ページ一覧、全画面、閉じる操作で最後まで読める。Webスライドは固有の動きを実行する。静止画の切替を、そのスキルのアニメーションと偽らない。
4. 同じ画面から、資料そのもののDL、使用スキル、日本語依頼文、制作条件へ進む。主操作は作品閲覧と利用であり、内部のログや検証用語を前面に並べない。
5. 「このスキルで作る」では、コピーできる具体的な日本語依頼文、必要な入力、導入手順、対応形式、フォント、原典と日本語派生版を得られる。架空のクラウド生成ボタンを設けない。
6. 元の209件も検索・カテゴリ別に閲覧できる。日本語制作事例のあるスキルには作品を紐付け、未制作のスキルはその事実が分かる。上流画像を当地制作の実例に見せない。

### 画面構成

- トップ：短い説明、実制作例の大きな入口、6カテゴリ、全スキルへの入口。作品とコレクションが主役。
- 制作例一覧：実際の資料名、用途、スキル名、枚数、形式、表紙＋中面。細かな検証記録は詳細へ。
- スキル一覧：既存209件を保持。検索、6分類、日本語制作事例ありの絞り込み。スター・旧信頼度を日本語品質の保証に使わない。
- 作品詳細／フロート：実資料、作者／使用スキル、成果物、依頼文、入力と制作記録、別方式との比較。
- 日本語版の使い方：導入から再制作、フォントの選択と導入、変更できる部分、出典と利用条件。

専用の「生成サービス」へ作り替えない。動きは作品閲覧を気持ちよくするために使い、読む資料に無関係な常時アニメーションは加えない。モデル名は対応確認がある場合だけ記載し、Opusへの言及だけから特定モデル専用にしない。

## 3. 初回で完成させる制作事例

3つの実在スキルを使用し、以下の6冊を制作する。各冊は表紙だけのデモでなく、受け手が内容を理解して次の行動を判断できる6〜8枚程度の資料にする。既存の自分自身を説明する4枚デモはこの件数に含めない。

| ID | 使用スキル | 資料・受け手 | 構成と見せる強み |
|---|---|---|---|
| cafe-pptx | hugohe3/ppt-master | 地域カフェの2号店出店提案／社内決裁者 | 8枚。結論、顧客、候補地比較、採算、運営、リスク、日程、決裁事項。比較表・数値・工程図を編集可能なPPTXにする |
| ec-monthly | hugohe3/ppt-master | EC事業の月次報告と改善計画／事業責任者 | 7枚。総括、KPI、前年・目標比較、チャネル、課題、施策、担当と次月判断。グラフと表、単位と計算の整合を示す |
| cafe-web | zarazhangrui/frontend-slides | 地域カフェの2号店出店提案／店内説明会 | cafe-pptxと同じ入力・数値・8枚。Web発表として組み替え、PPTX版との相互比較を設ける |
| git-onboarding | zarazhangrui/frontend-slides | 新入社員向け Git・レビュー入門／開発研修 | 7枚。安全な作業、ブランチ、PR、レビュー、競合、演習、確認項目。手順図と短いコード例を読める密度で使う |
| port-town | op7418/guizang-ppt-skill / Magazine | 週末の港町：回遊企画提案／企画担当 | 7枚。対象者、体験、行程図、集客導線、運営、測定、次工程。雑誌的構成でも具体的な企画として成立させる |
| knowledge-search | op7418/guizang-ppt-skill / Swiss | 社内ナレッジ検索 導入提案／業務改善担当 | 8枚。課題、利用場面、構成、方式比較、段階導入、権限と更新、評価、判断。構成図と段階計画を使う |

数値や会社は架空の制作サンプルと明記する。作例を充実させるための架空の統計・実在企業の成果を作らない。採算などの数値は入力で正本を定めて計算を確認する。カフェ2冊は同じデータを使い、方式ごとの違いを読み手が比較できるようにする。他4冊は内容とレイアウトを独立して設計し、文言を差し替えただけの複製にしない。

### 各冊に必ず付くもの

- `input/`：用途、読者、結論、元原稿、数値、制約。共有題材は共通の正本への参照を明示する。
- 編集可能な制作ソースと、PPTXまたは実行可能なHTML一式。PPTXには閲覧用PDFまたは実PPTXから出力したプレビューも付ける。
- 日本語の再制作依頼文。テーマだけでなく読者、ページ構成、渡す入力、出力形式、品質条件が入る。
- `PROVENANCE`または同等の記録：上流URL・commit、適用したSKILLと参照、プリセット／テンプレート、使用した実装、改良点、実行方法、フォント、成果物、検証結果。
- 表紙と中面のサムネイル、ページ数、形式、スキルへの逆リンク。配布物から原典・条件へ到達できる。

上流が指示型なら、AIがその指示とテンプレートに従って制作したと記録する。存在しないCLIの実行や、上流全機能の実行を主張しない。

## 4. 日本語派生スキルとして改善する内容

日本語で制作して露見した問題を修正し、その修正を次の制作でも使える形にする。単なるREADMEの翻訳や、名称変更のみを日本語対応と呼ばない。

- 日本語字形を持つ書体、本文／見出し／注記の役割、全角を含む長い見出し、自然な改行、禁則、行間、図表の単位と桁区切りを扱う。
- Noto Sans JP、Noto Serif JP、BIZ UD Gothicは目的に応じて使い分ける。採用ファイル・ウェイト・配布元・条件と、成果物を開く側の必要条件を記録する。推奨と埋め込み済みを混同しない。
- 提案なら決裁事項、報告なら比較基準と次の施策、研修なら練習と確認を含める日本語入力の例を同梱する。
- 該当上流の長所を保持する。PPT Masterのnative編集、Frontendのプリセット・ステージ・編集、Guizangの元テンプレート・ページ制御・演出を一つの共通rendererに均さない。
- 改良項目と、その項目を確かめた制作例を対応させる。導入手順の参照先が欠けたパッケージを配布しない。

初回3派生を保守可能な独立パッケージにする。全209件をフォーク済みと扱わない。次の対象選定は人気だけでなく、編集可能性、用途の不足、日本語の課題、当地実行条件、個別ライセンスで判断する。既取得候補9件は、制作済み／条件調査のみ／未調査を表示上も記録上も区別する。

## 5. データと出典の契約

`data/skills.json`の209件と分類、原典、説明を継承する。新規候補を追加するときは初期209件と追加分を区別し、実数から件数を表示する。旧カードの全画像を新制作例と数えない。

作品は一意のIDで管理し、少なくとも title、use_case、skill_repository、upstream_commit、fork_id、page_count、format、cover、preview、artifact_download、source_download、input、prompt、provenance、qa を持つ。フィールド名は既存実装に合わせてよい。作品とスキルは相互に辿れる。PPTX成果物を`kind: html`だけで表すなど、プレビュー形式と成果物形式を混同しない。

状態は次の事実を区別できればよい。利用者へ内部状態名を大量表示する必要はない。

| 対象 | 分ける事実 |
|---|---|
| スキル | 掲載のみ／条件を調査／日本語の制作事例あり／日本語派生配布あり |
| 画像 | 当地制作の成果物／上流公開作例／GitHub紹介画像 |
| 検証 | 実行結果／構造確認／実表示確認／人の採用判断 |
| PPTX | 編集可能なnative文字・図形／画像化したページ／実アプリ未確認 |

CC0の一覧と、各上流実装・テンプレート・書体・素材の条件を別管理する。MITの通知、AGPL派生の対応ソースと条件、書体のOFL等を配布対象に合わせて維持する。原典条件未確認の実装は複製配布しない。カタログに掲載できることと、コードを自由にフォーク・再許諾できることを同一視しない。

## 6. QAと受入条件

### 制作例

- 6冊が実在し、各資料が固有の受け手・目的・結論を持つ。出力数は作品manifestから数える。
- 全ページの日本語を実表示で確認する。文字欠け、はみ出し、極小文字、単位欠落、表とグラフの数値不一致を修正する。件数だけで品質を合格にしない。
- PPTXはMicrosoft PowerPointで実ファイルを開き、PNG/PDFに出力して確認する。変換入力SVGの表示だけで代替しない。文字・図形・ノートの構造確認も行う。もし実アプリ検証が失敗した場合は未検証と明記して当該受入条件を未達にする。
- HTMLは元のテンプレート／指示を適用し、全ページ・操作・動き・編集機能があるものの保存まで確認する。必要な依存とオフライン条件を記す。
- カフェ2冊は入力の数値・比較条件が一致し、形式の違いを示す相互リンクがある。

### サイトと配布

- 209件を検索でき、6カテゴリの件数が保持される。上流画像と当地作例の判別ができる。
- 制作例からスキルへ、スキルから制作例へ到達できる。DLリンクと依頼文コピーが実動する。
- フロートは実際の全ページを表示し、前後送り・現在位置・閉じる・Esc・キーボード操作が働く。閉じると元のカードへフォーカスが戻る。背面が誤操作されない。
- PCと狭い画面でプレイヤーが画面外へはみ出さない。スライドは比率を保ち、周辺UIが再配置される。動きを減らす設定を尊重する。
- 新たな作品の登録がmanifestと成果物の追加で行え、ページへ同じ情報を手書きで何重にも複製しない。
- DLしたパッケージ内に必要な制作ソース、依頼文、条件、手順があり、実在しないファイルへの参照がない。
- README、旧方針文書、サイトの表示が新しい実装と一致する。旧デモを新実例に算入しない。

公開前の状態は「ローカル初回実装・確認済み項目」を報告する。初回6冊・3派生は土台であり、「全209件検証済み」「日本人向けに完璧」「最強が完成」の証拠にはしない。外部公開・課金・main mergeは今回の実装完了条件に含めない。

## 7. 調査範囲と未確定部分

この仕様はユーザーの最初の依頼と2回の訂正、`03a2cb0`のREADME・トップHTML、現在の209件データと制作例manifest、3派生のSKILL、upstreams情報、当該リポジトリのAGENTSを確認して作成した。初期サイトの魅力は6分類と豊富な個別スキルであり、現在の自己紹介デモは実務資料の例ではないと判断した。

仕様策定時点では6冊を制作していない。上流全209件の実行・全条件の法的評価・PowerPointの実表示もこの文書だけで確認済みにはならない。実装者が原典・実ファイル・画面で検証し、結果を記録する。6冊という範囲と題材は、ユーザーへ再承認を要求せず進めるための初回の実装判断であり、ユーザーがこの数を指定したわけではない。
