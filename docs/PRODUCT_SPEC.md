# AIスライド制作スキル集：掲載リポジトリを実際に使った日本語ガイド

改訂：Astra／2026-10-13。ユーザーの最新訂正「取り上げた多くのGitHubリポを実際にこの環境で使い、スライドを作って、そのリポでこんな資料が作れるという案内にする」を正本とする。

## 1. 目的と前仕様の誤り

本サイトの主語は**掲載したGitHubリポジトリ**である。読者は「このリポでは、実際にどのような日本語資料を作れるのか」「自分の環境でどう使うのか」を、当地の実行・生成結果から確かめる。

209件・6分類の既存スキル集を出発点に、多くの掲載リポをそれぞれ実際に使い、リポ固有の方法で作った日本語資料、動かした環境、実行手順、成果物、原典と条件を結び付ける。紹介文の翻訳を超え、利用者が自分で使える案内へ育てることが目的である。

前仕様は、リポの実行範囲を広げる依頼を「実務題材の作品を増やす」へ置換し、3リポ×6冊を初回の完了条件にした。この限定はユーザーの要求ではなく、誤った実装判断だった。3リポ内で題材・スタイル・ページ数を増やしても、別の掲載リポを使ったことにはならない。6冊45枚の達成を、この製品の目的達成として扱わない。

既存6冊は3リポの利用を示す部分成果として利用できる。消去・巻き戻しは要求しない。新しい作業は、それ以外の掲載リポへ実行と生成を広げることを中心にする。

## 2. 対象となるコレクション

data/skills.jsonの209件を現物確認した。元の順序、作者、原典、説明、分類等の全フィールドを保持する。

| 元分類 | 件数 |
|---|---:|
| パワーポイント | 83 |
| ウェブスライド | 57 |
| 発表資料 | 29 |
| 資料制作総合ツール | 20 |
| ビジネス資料 | 13 |

分類は出力・用途の整理であり、実行方法が同じことを意味しない。CLI、MCP、エージェントへの指示型SKILL、固有テンプレート、文書・画像からの変換、外部APIを使う方式が混在する。原典から実際の入口を調べ、その方式を使う。カタログに含まれる総合ツール・一覧等は、どの機能がスライド制作に該当するかを特定する。制作機能のない一覧リポ自体を実生成済みにしない。

新しい有力リポの調査・追加も可能だが、元209件と追加分は区別する。古いスター数や元サイトの評価を現在の品質・利用条件・日本語対応の保証として使わない。

## 3. 情報構造と利用体験

### 基本単位

repositoryを主キーとし、次をそのリポに紐付ける。

1. **リポの案内**：名前、作者、原典、できること、出力形式、得意な用途。
2. **当地の実行状態**：未調査、調査済み、実行中、生成成功、検証済み、失敗、阻害条件あり等の事実。調査と生成を分ける。
3. **日本語作例**：該当リポ固有の入口から作った成果。入力、生成時の条件、実ファイル、全ページの閲覧、編集範囲。
4. **使い方**：試したOS・ランタイム・依存、具体的な導入と実行、渡す入力、出力先、必要な認証や費用の有無。
5. **日本語向け変更と原典**：固定したcommit、適用ファイル、日本語の改良差分、個別条件、配布できる範囲。
6. **未制作の理由**：不足する条件、実行時の具体的なエラー、解決に必要なこと、最後に確認した日。

作品はリポの使用結果であり、リポから離れた独立のテーマ集を主役にしない。同じリポの複数作品、同じ入力を使った異なるリポの比較は補助導線にする。

### 画面

- **トップ／リポ一覧**：6分類・検索で掲載リポを探す。カードの見出しはリポ名。「日本語作例あり」「使い方」「未制作と理由」が分かる。実制作のあるリポのカードには、そのリポで作った画像を使う。
- **リポ詳細**：「できること」→「このリポで作った日本語資料」→「この環境での使い方」→「自分の入力で作る」→「原典と条件」。未制作なら結果欄に具体的な状態を表示する。
- **フロート閲覧**：「作例を見る」で当該リポの実資料を全ページ再生する。PPTXは実PPTXの描画、HTMLは実HTMLを表示する。形式・文字編集可能性・ページ送りを明示し、閉じた後は元のリポへ戻れる。
- **比較・用途フィルタ**：同じ入力や目的でリポごとの出力を比べる補助。リポの実行範囲を作品数で水増ししない。
- **利用導線**：実成果物・入力・日本語依頼文・手順・派生スキルをその場から取得できる。原典のURLへ飛ばすだけでは利用案内の完成としない。

上流公開作例、GitHub紹介画像、当地生成物は出所を分ける。紹介画像だけのリポに「日本語で制作済み」と表示しない。動きやフロートは閲覧を助けるために使い、実行したリポの少なさを目立たなくするための装飾にしない。

## 4. リポごとに実行する内容

### 棚卸しと選定

元209件を対象に、原典入口、出力、依存、条件、当地での実行可能性を記録する。既に作例のある3リポ以外へ進む。優先順位は掲載上の重要性、異なる制作方式、用途・分類の広がり、当地での利用可能性、日本語利用者への価値から決める。

制作対象リストと進捗は明示し、実行可能な未着手リポを理由なく「将来対応」にして終えない。制作しやすい同一方式だけへ寄せた場合も、その範囲を示す。制約を解消できる安全な環境準備・修正は実行し、難しいことだけを理由に別の共通生成器へ置き換えない。

### 固有方式を実際に使う

| 原典の方式 | 必要な実行根拠 |
|---|---|
| CLI・生成スクリプト | コマンド、引数、入力、終了結果、生成ファイル |
| MCP・サービス | 起動・接続条件、使った操作と引数、結果、生成ファイル。接続だけで生成成功にしない |
| 指示型SKILL | 読んだSKILL・参照、制作依頼、採用した固有工程・テンプレート、生成ソースと出力。存在しないCLIを捏造しない |
| 固有テンプレート | 使用テンプレートのpath/hash、差分、元の表示・編集・出力機構を使った証拠 |
| 変換・再構成 | 元文書・画像と変換結果、実変換処理、どこまで編集できるか |
| 外部API等 | 必要条件と実際に行った操作の範囲。認証・課金が必要で使えなければ未制作として具体的に記録 |

原典を読む、ファイルをcloneする、LICENSEを保存するだけでは「使った」に数えない。共通の自作rendererで作り、リポ名だけ変えた成果を作例にしない。共通部品はデータ整理、サイトの表示、撮影、包装、検証などに使えるが、各リポの制作処理を代替しない。

### 生成物

題材はそのリポの強みを試すために選ぶ。日本語で意味の通る内容にし、表紙だけでなく、本文・図表・比較・手順などの中面まで確認できる資料を作る。全リポへ6〜8枚・特定の業務題材を一律に強制しない。変換スキルなら変換、学術スキルなら出典と論旨、画像型なら画像生成など、その機能を試す。

共有の小さな入力を比較に使ってよいが、原典の特徴を潰して同じ成果へ均さない。架空の会社・数値は明記し、計算の正本を保つ。

## 5. 再現可能な利用案内

実制作した各リポに次を揃える。

- 原典URL、commit/tag、SKILL・固有テンプレート・実装path、ファイルhash。
- 試したOS、Python/Node/アプリ等のバージョン、依存、フォント、外部サービスの要否。
- 作業ディレクトリを明示した具体的な導入・起動・制作コマンド、または実際のエージェント依頼／MCP操作。
- 入力資料、必要な設定、出力先、生成ソース、完成物、再表示に必要な依存。
- 実行ログと、生成成功・失敗・表示確認の証拠。秘密情報は残さず、必要な設定項目名だけ示す。
- 日本語の依頼例と、自分の資料へ置き換える箇所。
- 読める全ページプレビュー、実ファイルのDL、条件と制作記録へのリンク。
- 検証済みの環境と限界。ローカル固有絶対パスしかない手順にせず、利用者が置換できる相対パスや変数を添える。

カタログの一括組立スクリプトを示すだけでは、そのリポを使う方法の説明にならない。カタログ開発者向けの再構築と、利用者向けの原典／派生スキルの制作手順を分ける。

## 6. 日本語改良・ライセンス・阻害条件

日本語の字形、見出し・本文・注記の役割、英数と全角の混在、改行、禁則、単位、講稿を実制作で確認し、必要な改良を各リポの派生へ戻す。翻訳した入口だけで日本語品質を確認済みにしない。日本語の修正で原典の制作機能やデザインを別物にしない。

フォーク・配布は個別条件を確認して行う。元作者の通知、MIT／AGPL等の条件、対応ソース、書体・画像等の条件を保つ。サイトのCC0を掲載コードへ一括適用しない。全件のフォークを、全件の利用調査に先行する必須条件にはしない。利用と再配布で許される範囲が違う場合は、その違いを記す。

動かせないリポには具体的な記録を残す。例：必要なAPIの資格情報がない、課金サービスが必要、必須依存の特定バージョンでエラー、必要ファイルの公開がない、配布条件を確認できない。試行したコマンド・エラー・確認先と再開条件を添える。「未着手」と「試したが阻害された」を分ける。失敗・未制作を別ツールによる代替生成で埋めない。

秘密情報・課金・外部公開等は既存の承認境界に従う。認証を勝手に取得したり課金したりせず、進められる別リポの作業を続ける。

## 7. 記録と件数

- 元カタログ：data/skills.json。209件の全フィールドを保持。
- 原典の棚卸し：data/repository-audit.json。commit、tree、README／SKILL／条件ファイル等の取得・読取状態を保存する。機械的な棚卸しの完了は、個別の条件レビュー、環境構築、制作実行、採用の完了ではない。根LICENSEと特定エンジン・素材の条件差、archived状態も個別に読む。
- リポごとの案内と状態：data/project-workflows.json、または実装上導入する同等のリポ単位台帳。原典、環境、実行方法、run、作例、派生、阻害条件を参照する。
- 作品：data/case-studies.json等の実制作manifest。必ずrepositoryと実行記録へ結び付く。
- 入力・成果物：既存のexamples/cases/等を継続利用できる。新しい作品を既存6件固定の検証条件で排除しない。
- 旧試作：data/actual-examples.json等は歴史記録。現行の作例として採用する根拠がなければ現行件数に含めない。

掲載リポ数、調査済みリポ数、実行試行リポ数、生成成功リポ数、表示確認済みリポ数、未着手・阻害されたリポ数、作品数・ページ数を別に集計する。同じリポで何冊作っても、生成成功リポ数は1件である。ライセンス調査のみを実制作済みにしない。

## 8. 受入条件と進め方

**3リポ、6冊、45枚を製品の完了条件にしない。** 当地で多くの掲載リポを使った案内へ拡張できたかを、リポ単位の実績と未実施範囲から判断する。

- 209件を起点とする棚卸しと制作対象の記録があり、選定理由と未実施範囲が分かる。
- 既存3リポ以外の多くのリポで、それぞれ固有の方法を使った日本語成果を作り、リポ詳細から確認できる。
- 生成成功とするリポは、第4・5節の実行根拠、成果物、利用手順、原典と条件を持つ。単なる紹介カードの追加で達成扱いにしない。
- 動かせない対象は具体的な理由と再開条件を持ち、未着手を実行失敗として偽らない。安全に解消できる阻害条件は修正して再試行する。
- フロートで実成果物を最後まで見られ、原典・入力・実行方法・DLへ相互に辿れる。
- PPTXは実アプリで描画し、native文字・図形／画像化／ノート等を出力から確認する。HTMLは実際の表示・操作を確認する。チェックが通っただけで美術品質や人の採用を保証しない。
- 進捗報告は、何リポを調べ、何リポで何が生成でき、何が未着手・阻害されているかを中心にする。ページ数を中心に完了を説明しない。
- 一度の作業バッチの完了は、その対象の実行と案内整備の完了である。全体の目的達成や全209件実行済みと同一視しない。都合のよい少数を固定して依頼全体を閉じない。

元209件に外部サービスや特殊な条件を要するものがあるため、全件の生成成功を捏造しない。一方で「209件全部は無理」を理由に3リポの作例集へ縮めない。実行可能な対象への制作を継続し、部分成果と未実施範囲を正確に報告する。

外部公開・正式採用・main mergeは実装・技術確認とは別の状態。今回の仕様改訂は公開承認を追加しない。

## 9. 既存成果の扱い

PPT Masterの2冊、Frontend Slidesの2冊、Guizangの2冊は、それぞれのリポの実行例として使える部分成果。題材、制作ソース、PowerPoint描画、HTML、再現資料、フォント、プレイヤー、包装・検証部品は保全して活用する。

これらの品質を整えることだけで残りの掲載リポの実行を代替しない。以前の自己紹介デモや独立5スキルへの置換を再採用する意味でもない。今後の実装・資料・検証は、6冊固定の構成からリポ単位の実績が増える構造へ更新する。
